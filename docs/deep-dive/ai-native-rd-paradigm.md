# AI 原生研发——从流程到组织的范式重构

> AI 时代研发流程、组织与人才体系的方法论

---

> 代码行数增至 17 倍，但发布版本只增长 30%。这不是 AI 不行，而是大多数团队在用“老的生产关系"跑新的AI生产力”——IPD 已死，三节点当立。流水线式组织不变革，AI 生产力就无法释放。本文从一线实践及行业调研出发，给出从“**流程->组织->人才->协同**”的完整AI研发体系构建路线图。

## 一、变化：AI生产力


### 1.1 生产力变化——从"人×工具"到"人×AI Agent 阵列"

过去几十年，软件研发的生产力提升沿着一条线：更好的语言 → 更好的框架 → 更好的 IDE → 更好的协作工具。但这条线的本质没有变：**生产力 = 人 × 工具**。**人是唯一的生产主体**。

AI 带来的变化是：**软件研发第一次出现了第二类生产主体——AI Agent。** 这不是"更好的工具"，而是"新的生产主体"。

**生产力的公式从"人 × 工具"变成了"人 × AI Agent 阵列"。** 一个开发者可以同时调度单个/多个 AI Agent 完成不同任务，生产杠杆从线性变为指数级。

关键是 AI 的生产力还在大幅度提升，AI 研发在”代码开发→全流程研发→长程任务→并行任务”等维度都在大幅度进步，我们从几个递进的阶段去描述：

1. AI开发：目前我了解的研发团队，没有不用AI开发代码的，代码几乎100%由AI生成，人类开发者更多承担定义和判断类工作。
2. AI研发全流程：Claude Code 等可以直接拆解任务、创建文件、运行测试、修改代码，并且这些工作是在一个Loop中，一旦确定无需人的参与。
   > Russell观察：各个Agent应用都在内化Loop能力，而非需要加载类似Superpowers一样的skill。目前Claude Code调用Superpowers的触发几率我感觉是明显降低的。
3. AI长程任务：目前国内外各种Agent应用都在追寻"长程任务"，比如GLM-5.1可以"独立工作8小时"[^3]，虽然我认为还不能用于大部分生产工作，但是"长程任务"及"长程质量"作为AI的新目标，我相信很快就可以达到"好用"的水平。目前业内已经在尝试多Agent等方式，寻找长程任务的Scaling Law，尤其是在"写测试"，"重构"、"监控告警"等合适的场景里。
   > Russell观察：就编程而言，我的代码生成Loop一般控制在20-30分钟粒度，这主要是为了平衡产品方向和质量，但是现在的代码生成无论时长上限还是质量都比几个月前大大提升。现在基本我是"1-1.5小时思考和交互，半小时生成，1小时审核及调整"，完整研发一个循环的时长大概2.5-3小时，但是中间半小时生成时间，从设计到开发、测试甚至部署，基本不需要人交互。
   >
   > Russell观察⭐：“长程“不是唯一的指标，“准”且“快”的高质量输出比”长程“更重要。所以“快、准、长程“都好才是真的好。
4. AI并行开发：Claude Code、Cursor等都可以同时运行多个 Agent 在不同分支上并行开发（Git Worktree）
   > 注意，这只是AI本身能力的进步，我们这里还没有讲流程和组织的优化。

### 1.2  代码生产力1730% Vs 版本量130%——研发的瓶颈从"编码"到"人的判断"

MIT 与宾夕法尼亚大学 2026 年在 NBER 发布的工作论文[^1]追踪了 10 万名开发者：**代码行数增至 17.3 倍，但最终发布的软件版本只提升了 30%**。DX 对 400 多家企业的纵向追踪[^2]也印证了这一点：AI 工具使用率平均提升 65%，但中位 PR 吞吐只提升 7.76%。

这恰好揭示了核心问题：**AI 提的是 α 层（执行层）的效率——更快地完成任务；但营收取决于 β 层（判断层）的质量——知道该做什么任务、判断什么任务值得做。**

**AI 的能力优势在执行层，但”商业价值“在判断层。** 一个不解决用户需求的产品，即使写了 10 倍的代码，营收也不会提升。研发流程重构的重心不在"让编码更快"，而在"让判断更准"。

### 1.3 AI那么牛，公司是不是可以裁人了？——隐性知识的结构性约束

AI 可以降低"执行"的门槛，但无法降低"判断"的门槛。每个岗位都有"没做过就不知道"的隐性知识——设计的审美和一致性Sense、架构的判断和经验、测试的边界、运维的直觉，安全的意识等等。

这些隐性知识分为两层：

| 层次              | 内容                            | 处理方式             |
| --------------- | ----------------------------- | ---------------- |
| **冰山以上（可显性化）**  | 非功能性需求清单、测试方法论、安全审查清单         | 写成Agent，交给 AI 辅助 |
| **冰山以下（不可显性化）** | 审美、设计 sense、方案和技术判断、测试直觉、安全嗅觉 | 必须靠领域专家真人介入      |

这意味着：

- **技能门槛正在被重构**：各个岗位执行层的技能正在被 AI 快速覆盖，“古法“不可持续；SOP可以沉淀，标准化的经验很难依靠——这些都将被“AI驾驭”能力统一替换。
- **"一人团队"在生产场景下不合理**：一个人不可能同时具备所有领域的隐性知识，可能会有潜在的成本和风险，商用产品必然还是依靠团队。
- **资深员工的价值重估**：AI替代了”技能型“和”标准型“工作，但是隐性知识反而更加稀缺，所以”资深员工“，以及“AI驾驭能力强“、”熟悉业务懂技术的员工“，不仅不应该裁掉，反而因为其可以”快速、高质量“的开发出产品，而应该纳入后续AI研发团队。

### 1.4 结论：一切阻挡AI提效的，都将被重构

AI就是一辆坦克，它将摧毁所有挡它的“古城墙”。

代码生成成本趋近于零，过去围绕"编码瓶颈"建立的一切——流程、文档、组织分工、管理幅度——都需要重新构建。这种变化可以归纳为三个范式转移：**从流程为先到结果为先、从工程为先到业务为先、从职能部门到 AI 协同组织**，从而更加高效、灵活、专业。

## 二、流程：研发流程应该变成什么样

### 2.1 为什么传统 IPD 流程必须变

**核心原因：现有的 IPD 式软件研发流程已经不再适应生产力变化。**

**传统 IPD 流程**（7 环节线性单次）：

```
需求 → 产品 → 架构 → 设计 → 研发 → 测试 → 部署
```

传统的 7 环节线性单次流程（需求→产品→架构→设计→研发→测试→部署）是为"人执行"设计的——每个环节都需要人产出中间产物（PRD/架构文档/设计稿/测试报告/发布说明）给下一个人。

这个流程现在有几个问题：

1. 这套流程因为过于复杂且死板，发展到现在，很多已经变成了”为了流程而流程“ ，比如：大小需求都要维护文档，比如需求经常变化，文档还需要花大精力更新。
2. 为了保证“需求-设计-研发-测试”四重一致，反复拉大会，导致各岗位人员精力消耗，大大加重了各岗位人员的负担。
3. 最重要的，在AI时代，**这些流程的产出，已经不是AI时代所需要的**。如果依然保持这套体系，无异于“郑人买履”。

所以，我们需要的，不仅仅是创建每个流程的 Agent，而是应该根据 AI 时代的本质，从第一性原理出发，重新定义流程。

**AI 时代的研发是什么样子？** AI太快了，以至于可以略过中间过程，直接出结果，所以我们不再需要中间流程和节点，不再需要中间产物。我们第一次可以直接用迭代的"结果"取代"过程留痕"。

### 2.2 三节点循环模型（替代 7 环节线性链）

根据AI时代的编程共识，我认为传统的 7 环节线性链正在被**三节点循环模型**替代：

```
制定目标与约束 → AI 执行与验证 → 人判断与决策
       ↑                              |
       └──────── 反馈与迭代 ←──────────
```

不同粒度的任务在不同时间尺度上循环：微任务分钟级、小任务小时级、中任务天级、大任务周级；但无论如何，都是这个”基本 Loop”的迭代。

基于这个哲学，我们的输入和产出应该是什么呢？

**三节点循环（输入和产出）**：

```
人 (产品哲学+Roadmap+Spec) → AI 执行与验证 → 人 (Demo/成品判断)
       ↑                              |
       └──────── 反馈与迭代 ←──────────┘
```

传统流程节点不存在了，所以输入和产出也不同了。**"哲学 + 产品路标 (Roadmap) + Spec"循环，产品验证直接用原型，最终导出成品。**

**关键变化**：传统流程是人→人传递（需求→产品→开发→测试），每个环节都是"人看懂上一个环节的产出，然后做自己的工作"。新流程是人→AI→人循环，AI 承担了中间的"看懂→执行→验证"部分，人只需要在起点和终点做判断。

### 2.3 从产品哲学出发

> Russell观察：特指商业化产品，一句话项目或者简单的个人项目可以选择略过

这是很多人忽略的一点。产品的功能AI会帮忙细化，但是产品的哲学（产品定义、理念、工程化原则等）应该是我们凭着自己的Sense提前决策的。**这是产品的宪法**。

> Russell观察：这里有个诀窍，就是参考优秀开源项目。比如 DeepSeek Harness 就有类似于”一切皆插件”，”日志即真相”等核心工程理念。

先写产品哲学，再推导功能设计，再推技术选型。如果我们相信"人的需求，审美、品味、判断"依然具有价值，那么产品哲学应该是一款产品的核心壁垒——功能堆叠的产品 AI 也能堆，也能抄，但抄不走你的产品哲学，以及产品哲学之下的你的思考。

这种产品哲学驱动的方式，需要一套分层文档体系来承载：

**分层文档体系替代厚 PRD**：

- 产品哲学 + 术语表（最稳定，永不丢）
- → MVP 边界 + 产品 Spec（替代厚 PRD）
- → 模块 Spec（每个模块的 WHAT）
- → Demo / 原型（可执行的需求表达）
- → Roadmap（轻量意图地图）↺ 持续迭代

PRD 进化为"产品哲学 + 轻量 Spec + Demo"三位一体。PRD、架构文档没有消失，而是沉淀在对话和 Spec 里——什么时候需要任何材料（售前/营销/架构说明），用自然语言让 AI 从最新产品实时生成。

### 2.4 本文所称 Specification-Driven 开发（SDD）

Specification 定义 WHAT，AI 做 HOW。标准流程为：

> Russell观察：注意，这里的 SDD 不是传统意义上的规范驱动开发，传统的SDD混杂了“规范”和Spec(可执行规格）；而我认为公司规范、架构规则等应该作为 skill/agent 承载，在plan阶段协助定义specification。我个人观察，业界现在也是在这样做的。

```
philosophy（产品哲学）→ plan（技术方案）→ specification（可执行规格）→ tasks（原子任务）
→ AI 逐任务实现并自验证 → 迭代更新 Specification
```

Specification 是 plan 阶段的产出——基于产品哲学，通过架构设计、技术选型等方法论（skill），输出可执行的规格说明。产品级的 Specification 会随需求迭代而更新，任务级的执行完即归档。

> **Russell观察：按需工程化**AI能力之强，很多时候不需要过度工程。测试/架构/DDD等非功能性内容不是不做，是按需、按阶段做——核心模块严格，边缘模块先跑通再说。比如测试，不用追求单次的"单元测试覆盖率"，"全量测试"；只需要在 Spec 中声明"测试金字塔/分层测试"原则，并配置 Stop Hook 交付前门禁（单测+Lint，不过不交付），保证最终做到即可。

### 2.5 业务验证用 Demo，不用文档

用 Demo 取代中间文档，作为唯一的"产品现状"。Demo 随时对齐，快速协作校准，早期发现问题的调整成本远低于交付后（行业经验通常为 1/5 到 1/10），持续校准比一次性验收更可靠。

> Russell观察：目前很多Agent应用已经在开始推进“项目协作”能力，但是还都不强，如何在现有产品下，比如每个人都有Claude Code及产出的情况下，完成“团队级合作”大家可以根据自己的平台研究一下，在我整理好”最佳实践“之前，也可以私下交流。

### 2.6 进度从结果导出（仓库即事实）

受”敏捷”思想的影响，在传统开发流程里，我们有了太多的中间文档。尤其是周报、日报，大家花费大量精力。AI时代，完全可以减少甚至取消日报/周报，常规进度由Leader从仓库自动分析：

- **PR 合并频率**：衡量实际交付速度（被动自动抓取）
- **CI/CD 状态**：衡量质量——测试通过率、部署成功率（被动自动抓取）
- **Demo**：衡量用户价值——不是代码质量，而是"用户看到的是什么"（主动）
- **阻塞项清单**：衡量风险——哪些问题正在阻碍进展（人上报）

**仓库是唯一无法造假的进展来源。** 个人上报的进展报告在 AI 时代最不可靠——AI 可以生成漂亮的报告但代码没有进展（大家不要互丢AI垃圾）。Leader 不需要每天看仓库，看仓库的衍生指标和分析即可，异常时才介入。

### 2.7 敏捷的演变（仪式驱动 → 价值驱动）

敏捷不会消失，但从"仪式驱动"变成"价值驱动"。

**变的**：

- Sprint Planning → 按任务粒度：微任务小时级、中任务天级，不做两周的强行切分
- Daily Standup → 人看 AI 生成的进展摘要，只讨论阻塞和风险（不再"人人汇报"）
- Story Points → 基于 AI 执行时间的实际度量
- Sprint Review → 持续 Demo（不需要等到 Sprint 结束）
- Scrum Master → 从"流程守护者"变成"AI 教练 + 价值推动者"

**不变的**（Jim Highsmith 的警告[^4]："如果你在敏捷上失败了，你在 AI 上会失败得更惨"）：

- 快速反馈循环
- 向目标用户交付精准价值
- 可观测性和发布的可靠性
- 人做价值判断

**最终形态**：AI 增强的持续交付。不再有 Sprint 的固定边界，人不再"汇报进展"，管理方式从"管理人的进度"变成"管理 AI 的产出质量和人的判断质量"。

### 2.8 本章结论：从"流程为先"到"结果为先"

> Russell观察：大白话，talk is cheap, show me the **DEMO**.

## 三、组织：AI时代的研发组织应该是什么样

### 3.1 职能分工的瓦解与重构

传统研发组织结构是"职能团队"——前端组、后端组、测试组、运维组。这种结构的前提是"每个职能有不可替代的专业技能，需要独立管理"。当 AI 承担了所有的工作，传统职能的边界就被模糊了。

**不是"岗位被 AI 替代"，而是"环节的边界在消失"**——当一个 AI Agent 做好Spec，并在一个Loop里写完代码、自动测试、修复 bug，传统意义上的“产品”，“架构”，"开发"和"测试"等已经融为一体。

### 3.2 按价值流划分（替代职能分工）

**"价值流"是用户概念**（"用户从注册到登录的完整体验"），是按"一个小组可以独立交付"划分的。

按价值流划分的好处是：每个小组的目标是"用户完成某个旅程"，而不是"维护某个职能领域"——这自然对齐了价值出口。

| 传统职能分工             | 价值流划分（AI 时代）       |
| ------------------ | ------------------ |
| 按技能划分（前端组、后端组、测试组） | 按用户旅程划分（一个小组端到端交付） |
| 一个功能需要多个组协作        | 一个小组独立完成用户旅程       |
| 目标是"维护好我的职能领域"     | 目标是"用户完成某个旅程"      |

### 3.3 "一人团队"的合理性和不合理性

很多老板看到AI很强，尤其是有技术背景的老板，一人实现了80%的功能，但是一旦想上线，发现剩下的20%要花费自己80%的精力，而且有些自己永远做不好，这就涉及一个命题——”一人团队“在生产场景下是否合理。

我的判断是“一人团队”对于Demo、小型项目、甚至SLA要求不高的商业项目都是可以的。

但是对于绝大多数生产场景是不合理的，主要有以下几个原因：

1. **吞吐量**：一个人的吞吐量有限，尤其是想对标竞对取得“相对优势”的团队来讲。**"快速反应，快速落地"现在比以往任何时候都更重要**，一个人很难兼顾从需求到上线的所有流程。
2. **高低价值错配**：一个人可以做全栈，代表这个人的“高价值”，但是项目中不可避免的有“低价值”但很繁琐的工作，是一种资源错配。
3. **无法掌握所有隐性知识**：最重要的，AI越强，项目跨的领域越大，一个人不可能同时具备所有领域的隐性知识——产品判断、架构判断、设计 sense 、审美能力、安全嗅觉...。AI 降低了执行门槛，但判断力需要领域经验，一个人无法覆盖所有领域。

目前行业内的实践是 **3-5 人”特战小组“**。

但是综合考虑几点：

1. **”特战小组“是相对稳定的”最小颗粒“**：对某个业务项目，小组这个组织必须相对稳定，因为潜在的交流，实践的经验，业务的背景知识不容易迁移；
2. **”特战小组“需要有一定的弹性和联合作战能力**： 公司的项目大小不一，对于像快速上马的、中大型的项目，不能只委托给一个小组。
3. **“特战小组”需要有“资深外援纵向支撑“**：传统研发有”架构师“团队，AI时代，一样需要“资深外援”，因为项目需要的高阶经验和专项能力、工具，并不是每个小组的成员具备的；具备高阶能力的人，也不需要全程参与某个具体小项目。

因此，组织结构需要同时满足三个条件：小组稳定、弹性协同、高阶能力可及。


### 3.4 双层矩阵（战略层 + 产品线 + 弹性池）

以下是一种满足上述三个条件的组织结构：

```
┌──────────────────────────────────────────────────┐
│                  战略层                           │
│    CTO + 架构委员会                               │
│    职责：技术战略方向、架构决策、跨产品线资源分配      │
├──────────────────────────────────────────────────┤
│              产品线 A         产品线 B         产品线 C  │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐        │
│  │ 产品 Owner│  │ 产品 Owner│  │ 产品 Owner│        │
│  │ (判断层)  │  │ (判断层)  │  │ (判断层)  │        │
│  ├──────────┤  ├──────────┤  ├──────────┤        │
│  │ 模块 Owner│  │ 模块 Owner│  │ 模块 Owner│        │
│  │ + AI 阵列 │  │ + AI 阵列 │  │ + AI 阵列 │        │
│  ├──────────┤  ├──────────┤  ├──────────┤        │
│  │ 模块 Owner│  │ 模块 Owner│  │ 模块 Owner│        │
│  │ + AI 阵列 │  │ + AI 阵列 │  │ + AI 阵列 │        │
│  └──────────┘  └──────────┘  └──────────┘        │
├──────────────────────────────────────────────────┤
│              弹性小组（独立组织单元）                │
│   全栈 AI 驾驭者，按需调配到业务组          │
│   日常：内部平台 40% + 技术预研 20% + 调配 30% + 沉淀 10% │
├──────────────────────────────────────────────────┤
│                  横向支撑层                        │
│   领域专家池（按需介入）：资深架构师、安全专家、       │
│   性能专家、设计专家、测试专家                        │
└──────────────────────────────────────────────────┘
```

- **全员**："特战小组"里，**所有的角色都要“AI原生”（注意，这是原则）**，**都要下场Coding，**“特战小组”太小，无法支持单独的管理人员。“成员”可以有职能倾向，做虚线拉通，这是合理且值得被尊重的，比如产品、设计、测试转过来，可以继续承揽相关工作，但是不再区分具体职能岗位。
- **产品 Owner**：负责拉通产品的目标定义、价值判断、战略对标、功能对齐。
- **模块 Owner**：常规技术架构、目标拆解、AI 调度、AI 产出审查。每个模块 Owner 管理自己的 AI Agent 阵列（编程-测试-部署等子Agent团队）。

### 3.5 支撑机制（弹性小组 + 横向支撑层）

**弹性小组（人力池）**：

- 全栈 AI 驾驭者，按需调配到业务组
- 应对吞吐量波动，解决"特战小组弹性不足"的问题
- 日常：内部平台 40% + 技术预研 20% + 调配 30% + 沉淀 10%

**横向支撑层（能力池）**：

- 领域专家按需介入
- 不是所有职能都需要横向专家，按项目类型决定：

| 项目类型        | 需要横向专家（举例）              |
| ----------- | ----------------------- |
| 内部工具/后台系统   | 可能一个都不需要                |
| B 端 SaaS 产品 | 架构 +性能 + 安全（设计可选）       |
| C 端消费产品     | 前端规范 + 设计 + 架构 +性能 + 安全 |
| 云平台/基础设施    | 运维 + 性能 + 安全            |
| 金融/医疗/合规    | 安全 + 合规（性能可选）           |

- 专家介入时机：首先，在 产品级Spec 阶段介入（审查项目级 Spec 中的领域约束），不是"研发完成后"才审查代码；其次，项目的相关专家Skill可以被横向专家沉淀，应用在整体流程里；最后，在流程后期进行审视、协同补充相关内容。
- 一个专家尽可能负责 3-5 个项目，太多就只能做表面审查——而表面审查 AI 也能做

### 3.6 多小队协同（声明式护栏 + 契约 + 联合验收）

单个特战小组适合中小型项目，但大型项目需要多个小队并行。

> Russell观察⭐：目前市面大部分AI应用产品，都还没有做好多人协同功能。更不用说多团队协同。实际操作中，多人、多团队协同更多还是在传统方式上的土办法。土办法也是没问题的，先用起来，不过这里要提的是一种最佳实践。

多小队协同不是简单的"人多力量大"，而是需要解决三个问题：如何保证架构一致性、如何管理小队间依赖、如何协调跨队变更。

- **声明式护栏，而非中心化审批**：架构规则写成机器可执行配置（全局 CLAUDE.md、CI 钩子、架构巡检 Skill），违规自动拦截，无需逐个人工评审。成立架构守护团（专家池抽取，或每小队 1 名架构代表，周同步）仅做规则制定与例外裁决，不干预具体开发。
- **边界与依赖管理**：**每个小队负责一个完整业务域**，端到端全栈交付，小队之间通过 API/事件交互，禁止跨小队直接修改代码。跨小队依赖先定义轻量契约（OpenAPI/异步事件 Schema），配合自动化契约测试。**契约要机器可读、变更要 AI 辅助快速传播**。一端变化 → AI 分析影响范围 → 快速协同另一端变更 → 自动化契约测试验证。
- **跨小队协同机制**：共享能力中心（公共 Skill 库/组件库/脚手架）、跨小队 Issue 流转 Skill、团队群周同步（仅对齐目标与风险）、大版本联合验收（全链路测试 Skill + 人工核心业务验收）。

### 3.7 本章结论：从"职能部门"到"AI 协同组织"——小组稳定、弹性协同、高阶能力可及

## 四、人：组织里的人应该是什么样的

### 4.1 核心能力：从"会做"到"会判断"

AI时代，各种岗位的技能很多被AI取代了，技能部分统一为“AI驾驭技能”。因此，最核心的变化：**人的核心能力从"会做"变成"会判断"。**

| 传统核心能力 | 新核心能力       | 为什么                              |
| ------ | ----------- | -------------------------------- |
| 编码能力   | 代码审查与架构判断   | AI 能写代码，但人需要判断 AI 写的代码是否合理、是否可维护 |
| 测试能力   | 质量风险判断      | AI 能跑测试，但人需要判断"哪些场景 AI 可能没覆盖到"   |
| 需求分析   | 需求抽象与约束定义   | AI 能生成需求文档，但人需要定义"什么是对的"         |
| 项目管理   | 目标拆解与 AI 调度 | 不再管理"人做什么"，而是管理"AI Agent 做什么"    |

### 4.2 生产级产品小组内的能力结构（产品 Owner + 模块 Owner + 领域审查者）

**基础能力**：所有成员都必须具备 Coding 能力，直接参与产品建设。

**差异化能力**：

| 角色           | 专业能力                | 负责                                         | 隐性知识来源   |
| ------------ | ------------------- | ------------------------------------------ | -------- |
| **产品 Owner** | 产品判断 + 战略对齐         | 定义产品目标、价值判断、战略对齐，同时下场使用 AI                 | 产品经验     |
| **模块 Owner** | 目标拆解 + AI 调度 + 架构判断 | 定义"做什么"和"不做什么"，审查 AI 产出的架构合理性              | 产品/架构经验  |
| **领域审查者**    | 特定领域的隐性知识           | 审查 AI 产出中该领域的问题——安全性、性能、可维护性、测试覆盖、设计 sense | 做过该岗位的经验 |

**最小生产级小组 = 产品 Owner + 模块 Owner + 至少一个领域审查者。** 领域审查者来自横向支撑层（3.4），可以不是全职，可以是一个资深专家同时服务多个小组。但对生产级产品很建议配置——因为专家的隐性知识是稀有且必要的。

**小组内要有不同的能力，但必须都有“价值判断能力”**：知道"什么是对的"。产品 Owner 从战略和产品角度判断，模块 Owner 从架构和技术角度判断，领域审查者从专业深度角度判断。三者都要能回答"这个方案对不对"——只是从不同角度。

### 4.3 小组规模按项目分级

| 项目规模 | AI 时代合理人数   | 说明                                 |
| ---- | ----------- | ---------------------------------- |
| 微型   | 1-2 人       | AI 承担 80% 编码 + 测试 + 部署，1-2 人做判断和把关 |
| 小型   | 2-3 人       | 至少 2 人互相审查，避免单人盲区                  |
| 中型   | 3-5 人       | 多模块并行，5 人约可覆盖传统 10-15 人的工作量        |
| 大型   | 3-5 人 × 多小组 | 多个小组并行，每个小组 3-5 人                  |

**"2 人"是所有场景的底线**：两个人互相审查，避免单人盲区。微型项目 1 人，但必须有一个外部审查者（不是全职，但必须在关键节点介入）。

### 4.4 资深员工的价值重估与新人培养路径

**现有员工的价值重估**：

- 不是"AI 替代了员工的编码能力"，而是"员工的编码等常规技能不再稀缺，但AI驾驭能力、判断力、隐性知识（知道什么代码会出问题、知道什么设计会翻车）变得更加稀缺"。
- 资深员工从"最好的执行者"变成"AI 驾驭者的导师和审查者"。他们的价值不再是"自己做得多快"，而是"帮 AI 驾驭者避开多少坑"。



**新人培养路径变化**：

- 新人：新人不再从"执行"开始（因为 AI 能做执行），而是从"审查 AI 产出"开始——通过审查 AI 的代码、测试、设计，来积累隐性知识。这比"自己写代码"更快地积累判断力。

> Russell观察⭐：但是如果新人不沉淀知识，始终不去了解AI驾驭的系统性知识，AI驾驭的底层知识，各种传统技术的底层知识（组件、架构、解决方案等），就很容易被取代。

- 晋升路径：特战小组队员 → 弹性小队/领域专家（支撑多业务） → 技术负责人/横向 Leader → 技术 VP/CTO

### 4.5 本章结论：技能门槛被重构，判断力成为核心稀缺资源

## 五、协同：不同规模的项目应该怎么协同

前面定义了"人"和"组织"，但组织不是静态的——不同规模的项目需要不同的协同方式。从 1 人 + 多 Agent 到多小队并行，协同机制随规模变化。

### 5.1 微型/小型项目：一人多 Agent / 2-3 人小组

**一人多 Agent 模式**（微型项目）：

```
全栈工程师
    ├── Coding Agent A（前端）
    ├── Coding Agent B（后端）
    ├── Testing Agent（自动化测试）
    └── DevOps Agent（部署）
```

一个人的管理半径被 AI 放大。以前一个人管一个模块，现在一个人管一个完整项目。关键是：这个人需要同时具备产品判断力和架构判断力——不再是"我会写代码"，而是"我能在 AI 生成的 10 种方案中选对的那个"。

**2-3 人小组**（小型项目）：分模块合作，至少 2 人互相审查，避免单人盲区。


### 5.2 中型项目⭐：3-5 人特战小组（Day 0-7 周期）

**核心原则**：主责专精 + AI 全栈补位。不是消灭分工，而是用 AI 拉平能力差。3-5 人小队的标准配置与 AI 赋能方向：

| 角色       | 主责领域            | AI 补全能力                 |
| -------- | --------------- | ----------------------- |
| 产品/需求负责人 | 需求定义、用户故事、验收标准  | 快速生成原型、接口定义、测试用例初稿      |
| 架构师      | 技术选型、模块划分、公共组件  | 落地项目脚手架、架构校验规则、通用 Skill |
| 前端主程     | 核心交互、组件体系、性能优化  | 页面逻辑、对接接口、样式开发、单测       |
| 后端主程     | 核心业务逻辑、数据库设计、性能 | CRUD 接口、数据迁移、工具脚本       |
| 测试/质量负责人 | 测试策略、质量门禁、核心用例  | 自动化用例生成、回归测试、安全扫描       |
| 部署/运维负责人 | 环境配置、CI/CD、监控告警 | 部署脚本、故障排查、资源优化          |

**Day 0 – Day 7 项目周期**：

| 阶段      | 串行锚点（必须等）                                | 并行（可同时推进）                                               |
| ------- | ---------------------------------------- | ------------------------------------------------------- |
| Day 0   | 产品哲学 → MVP 边界 → 术语表 → 模块拆分（1-2 人锚定 Spec） | 架构师与产品 Owner 半串行咬合                                      |
| Day 1-2 | 公共组件契约、CI/CD 基线                          | 框架搭建、各模块 Skeleton、设计系统                                  |
| Day 3-5 | 跨模块接口变更需同步                               | **各垂直模块内部全栈开发完全并行**（**Mob Programming** 或一人编排多 Agent 并同步） |
| Day 5-6 | 集成与联调                                    | Dogfooding、Bug 修复、增量 Spec                               |
| Day 7   | 发布决策 + 灰度/回滚预案                           | 监控、回滚演练                                                 |

满负荷的关键：让 AI 承担"跨工种衔接"的重复劳动，人类只做"模块边界决策"和"跨模块协调"。3-5 人不是"3-5 个工种"，而是"3-5 个端到端模块 Owner"。

### 5.3 大型项目：多小队协同（接口契约 + 领域专家介入）

- **接口契约模式**：架构委员会定义接口契约（API Schema、数据格式、性能 SLA），各小组的 AI Agent 自动生成符合契约的代码和测试，跨小组的接口验证由 AI 自动完成，人只介入"AI 报错"的情况。
- **小组间的协同发生在三个层面**：
  - **目标对齐（人→人）**：产品 Owner 和各个模块 Owner 之间的对齐会议。频率：周级。
  - **接口对齐（人→人，AI 辅助）**：两个模块 Owner 之间对齐接口。AI 可以生成接口文档、Mock 数据、自动化验证，但**"接口的设计决策"是人做的**。频率：天级（按需）。**最佳实践：两人一起现场用 AI 输出**，即时消除理解偏差（30 分钟内完成，比异步对齐节省数倍）。
  - **冲突解决（人→人，AI 预警）**：当 AI 发现两个模块的实现存在冲突，AI 自动预警，然后两个模块 Owner 介入解决。**AI 预警，人决策**。频率：按需。

### 5.4 战略项目：价值出口对齐 + 架构委员会

**价值出口对齐模式**：

```
公司战略层（CEO/CTO 确认战略目标）
    ├── 业务线 A（组织目标 → AI Agent 阵列）
    │   └── 价值出口：该业务线对战略目标的贡献
    ├── 业务线 B（组织目标 → AI Agent 阵列）
    │   └── 价值出口：该业务线对战略目标的贡献
    ├── 横向协同层（AI 自动校验各业务线接口一致性）
        └── 冲突自动上报 → 人介入决策
```

战略项目启动时，先定义每个参与组织的"价值出口"——这个组织完成这个项目，对公司的战略贡献是什么。AI 自动校验各组织之间的输入输出是否匹配，冲突自动上报给战略决策层，由人做最终判断。

### 5.5 小组间的人与人协同

| 协同场景 | 谁和谁                     | 做什么                                          | 频率    | AI 辅助什么             |
| ---- | ----------------------- | -------------------------------------------- | ----- | ------------------- |
| 目标对齐 | 产品 Owner ↔ 模块 Owner     | 产品 Owner 定义"这个模块要达成什么"，模块 Owner 确认"我能做到什么程度" | 周     | AI 生成目标拆解草案，人确认和调整  |
| 接口对齐 | 模块 Owner A ↔ 模块 Owner B | 两个模块 Owner 约定接口格式、数据格式、交互时序                  | 天（按需） | AI 生成接口文档草案，人确认     |
| 领域审查 | 领域审查者 ↔ 模块 Owner        | 领域审查者审查模块 Owner 的 AI 产出，指出隐患                 | 天（按需） | AI 生成审查清单，领域审查者逐项确认 |
| 冲突解决 | 模块 Owner A ↔ 模块 Owner B | 两个模块 Owner 讨论接口或逻辑冲突，协商解决方案                  | 按需    | AI 标记冲突位置，人讨论解决方案   |
| 战略对齐 | 产品 Owner ↔ CTO/架构委员会    | 产品 Owner 汇报产品线进展，CTO 做战略判断和资源调整              | 月     | AI 生成进展报告，人做战略判断    |

**一句话总结**：小组之间的协同，AI 承担"发现冲突"和"生成方案"的部分，人承担"判断什么是对的"和"做最终决策"的部分。**AI 让协同更高效，但没有消除协同**——因为协同的本质是"两个人在各自领域做了判断，这些判断需要对齐"。

> Russell观察⭐：AI没有消除协同，但是AI会逐步取代低级协同。多Agent的协作，一个人或者一个主Agent完全可以管理远超7个的SubAgent。“硅基组织”的概念让Agent之间还有架构概念。

### 5.6 吞吐量弹性：核心固定 + 弹性池

5 人小组在小项目上完全没问题，但一旦涉及更大或更小的项目，吞吐量弹性不如传统职能部门。弹性池的整体结构详见第三章 3.4-3.5 节，这里聚焦弹性池的运转机制设计：

以 50 人团队为例：40-42 人固定业务组 + 8-10 人弹性池（约占 16-20%）。

弹性池关键设计：

- **日常做什么**：40% 内部平台开发 + 20% 技术预研 + 30% 按需调配 + 10% 知识沉淀
- **调度周期**：季度调度、周级响应（不能按天调度，上手成本会吃掉弹性价值）
- **绩效**：业务 Leader 40% + 弹性池 Leader 60%（弹性池 Leader 有一票决定权，保护成员不被过度压榨）
- **个人发展**：独立晋升通道；薪酬举例可比同级别业务组成员高约 10-15%（补偿稳定性损失）；弹性小组经历被视为"高潜力人才"标志
- **稳定性保障**：每人每季度最多调配 2 次，每次不超过 4 周；成员有"调配否决权"

### 5.7 本章结论：协同机制随规模变化，端到端交付是组织设计的第一原则

## 结语

生产力改变生产关系，生产关系影响生产力。

编码生产力爆发，围绕"编码瓶颈"建立的一切——流程、组织、管理幅度——都将被推倒重来。

这不是预言，这已经在发生——关键是我们如何适应它。

现在研发组织只有两种：用"人 + AI 阵列"重构生产关系的新物种，和还在用IPD流水线追赶坦克速度的旧军队。前者定义规则，后者被淘汰。

城墙正在倒塌。穿过裂缝的人，定义下一个时代。
