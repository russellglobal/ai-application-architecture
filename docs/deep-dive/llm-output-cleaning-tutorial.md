## 1. 开篇：一个真实的失败案例

### 1.1 凌晨 3 点的告警

这是 StratSapien （锦囊·商业可行性初筛平台）项目上线第二周的一个凌晨。监控系统突然告警：大量商业分析报告的 PDF 导出失败，用户交付链路中断。

排查后发现，根本原因是 LLM 输出的结构化数据格式出了问题。我们期望的格式是这样的：

````
<!-- METADATA -->
```json
{
  "step": 2,
  "market_size": {
    "tam": { "value": 500, "unit": "亿" },// 总潜在市场
    "sam": { "value": 200, "unit": "亿" },// 可触达市场
    "som": { "value": 50, "unit": "亿" } //可获得市场
  }
}
```
````

但那天晚上，LLM 实际输出的是这样的：

````
好的，作为商业分析专家，我来为您执行 Step 2 的市场规模测算。

## Step 2: 市场规模测算

根据行业研究报告，结合 top-down 和 bottom-up 两种方法...

<!-- METADATA
{
  "step": 2,
  "market_size": {
    "tam": {"value": 500, "unit": "亿"},
    "sam": {"value": 200, "unit": "亿"},  // 这是可服务市场
    "som": {"value": 50, "unit": "亿"},
  }
}
如果有任何疑问，欢迎继续讨论！
````

**这段输出里至少藏着 6 个问题**：

1. **对话式开场白**：「好的，作为商业分析专家，我来为您...」
2. **标志位格式错误**：`<!-- METADATA` 后面没有使用 `-->` 闭合
3. **JSON 被塞进注释里**：整个 JSON 在 `<!-- -->` 内，不是独立的代码块
4. **JSON 内含 `//` 注释**：`// 这是可服务市场`
5. **JSON 尾逗号**：`"som": ...}` 后面多了一个逗号
6. **对话式结束语**：「如果有任何疑问，欢迎继续讨论！」

我们的代码用单条正则去匹配标准格式，匹配失败 → JSON 提取返回空 → 跨文件一致性校验崩溃 → PDF 导出中断 → 用户看到 500 错误。

### 1.2 这不是 bug，不100% 保证输出准确，是 LLM 的本质

传统 API 的输出是确定性的：我们定义 schema，它返回 JSON。但 LLM 的输出本质上是**概率采样**的结果——同时为了保证输出结果的多样性以及隐私保护，同一个 prompt 在不同时间、不同上下文中可能产出格式迥异的输出。

⭐Russell 经验：**面向失败编程，是处理大模型结构化输出的第一原则。**

我们不能假设 LLM 会严格遵守格式，我们只能假设它**偶尔会违反格式**，然后为此构建防御。

> **灵魂问题**：为什么连“最强的模型”都没法 100% 输出合格 JSON？
> 答案不是「模型不够强」，而是「LLM 的输出本质上是文本，不是数据」。要把它从「文本」变成「数据」，必须有专门的解析层。

## 2. 失败模式分类

我们花了 6 个版本迭代，收集了 LLM 输出的所有"疯狂"行为。按**问题本质**分成 5 类（而不是按严重程度），因为同一类问题往往能用同一类方法解决，逻辑如下：
```
JSON标志位坏的，让我们找不到它——》即使标志位没问题，也可能有”对话式开头”等冗余内容——》没有冗余内容，但是JSON格式不对——》JSON本身没问题，但是Markdown原因，导致渲染出错——》（其他需要兜底的异常可能）
```

### 2.1 标志位变异

为了在长文本中定位结构化数据，我们通常在 prompt 中约定一个标志位（如 `<!-- METADATA -->`），LLM 应在标志位后输出 JSON。但 LLM 经常"忘记"或"变异"这个标志位。

**典型坏样例**：

| 现象 | 示例 | 体感频率 |
|------|------|---------|
| 标志位完全缺失 | 直接输出 `{ "step": 2, ... }` | 高（小模型尤甚） |
| 标志位未闭合 | `<!-- METADATA\n{...}` （没有 `-->`） | 中 |
| 自创闭合标签 | 输出 `<!-- /METADATA -->` | 低 |
| JSON 被塞进注释 | `<!-- METADATA {...} -->` | 中 |
| 自创标志位名称 | `<!-- META -->`、`<!-- JSON -->` | 低 |

### 2.2 对话式开场白/结束语

LLM 在训练中学会了"**礼貌对话**"，即使我们明确要求"直接输出结构化内容"，它仍可能先来一段寒暄。

**典型坏样例**：

```
// 开场白
好的，作为商业分析专家，我来为您执行 Step 2...
作为行业分析师，我已整合多方数据...
基于以上分析，我为您总结如下：

// 结束语
如果有任何疑问，欢迎继续讨论！
希望这份分析对您有帮助。
如需进一步细化某一部分，请告诉我。
```

**体感频率**：高。几乎所有对话模型都有这个倾向，尤其是经过"对齐训练"的模型。

### 2.3 JSON 本身的问题

即使 LLM 输出了"看起来像 JSON"的内容，JSON 内部也可能有各种语法错误。

**典型坏样例**：

| 问题类型 | 示例 | 体感频率 |
|---------|------|---------|
| 尾逗号 | `{"a": 1, "b": 2,}` | 高 |
| 单引号 | `{'name': '测试'}` | 中 |
| 键名缺引号 | `{name: "测试"}` | 中 |
| JSON 内嵌注释 | `// 这是说明\n{"a": 1}` | 中 |
| 未转义换行符 | `{"desc": "第一行\n第二行"}` （字面换行） | 中 |
| 未闭合 | `{"a": 1, "b":` （生成到一半停了） | 中（长 JSON 常见） |
| 数字精度溢出 | `"roi": 99999999999999999999` | 低 |

### 2.4 Markdown 格式污染

LLM 喜欢用 Markdown 来"美化"输出，但这些美化经常破坏 JSON 结构。

**典型坏样例**：

````
// JSON 中间插了加粗说明
{
  "tam": **约 500 亿**,
  "sam": 200
}

// JSON 被代码块包裹，但语言标签写错
```JSON
{"step": 2}
```

// 嵌套列表用 4 空格缩进，被渲染器误解析为代码块
* 父列表项
    * 子列表项（被 Markdown 解析为代码）
````

**体感频率**：中。长输出场景尤其常见。

### 2.5 其他（兜底场景）

前 4 类覆盖了 95%+ 的场景，但总有 5% 的边缘情况：

- **输出截断**：长 JSON 生成到一半触达 `max_tokens` 限制，戛然而止
- **多段 JSON**：LLM 输出了多个独立的 JSON 对象，不知道哪个是想要的
- **中英文括号混用**：`{"a": 1｝` （右侧是中文括号）
- **嵌入了代码注释**：`{/* comment */ "a": 1}` （React JSX 风格）
- **完全乱序**：JSON 和正文彻底混在一起，无法分离

**体感频率**：低。但一旦出现，普通正则完全失效。

## 3. 解决方案演进史

我们用了 6 个版本、跨越 4 个阶段，才把稳定性从 60% 提升到 99.99%+。每一个阶段都源于上一个阶段的"过不去"。

### 3.1 第一阶段：天真假设（稳定性 ~60%）

**思路**：LLM 会严格按 prompt 要求输出，用一个正则就能搞定。

**实现**：

```python
pattern = r"<!-- METADATA -->\s*```json\s*(.*?)\s*```"
match = re.search(pattern, content, re.DOTALL)
```

**结果**：60% 的情况下正常工作。强模型（GPT-4、Claude 3.5）成功率约 70-80%，小模型（DeepSeek-V3-lite）只有 30-40%。

**核心局限**：**完全依赖模型的自觉性，无任何容错**。LLM 偶尔忽略 `<!-- METADATA -->` 前缀，或者只输出 ```` ```json ```` 没有闭合 ```` ``` ````，正则就彻底失效。

### 3.2 第二阶段：多层正则覆盖（稳定性 ~85%）

**思路**：既然 LLM 会"变异"标志位，那就多写几条正则，覆盖更多格式。

**实现**：

```python
# 标准格式
pattern1 = r"<!--\s*METADATA\s*-->\s*```json\s*.*?```"
# 旧格式（JSON 在注释内）
pattern2 = r"<!--\s*METADATA\s*.*?-->"
# 裸 JSON（无标志位）
pattern3 = r'\{\s*"step"\s*:\s*\d+.*?\}'
```

**结果**：稳定性提升到 85%。

**核心局限**：**正则处理不了嵌套结构**（如 JSON 内含嵌套对象时 `(.*?)` 会过早截断），**修不了语法错误**（尾逗号、单引号、注释），**也救不了截断场景**。正则越写越复杂，但总有漏网之鱼。

### 3.3 第三阶段：括号栈兜底（稳定性 ~95%）

**思路**：正则搞不定嵌套结构，那就换一种不依赖正则的算法——**括号栈法**：从任意位置找到第一个 `{`，用计数器跟踪 `{` 和 `}` 的平衡，当计数器归零时就拿到了完整的 JSON 对象边界。

**实现**（核心代码 10 行）：

```python
def extract_json_by_bracket(text: str) -> str | None:
    depth = 0
    start = None
    for i, ch in enumerate(text):
        if ch == '{':
            if start is None:
                start = i
            depth += 1
        elif ch == '}':
            depth -= 1
            if depth == 0 and start is not None:
                return text[start:i + 1]
    return None
```

**结果**：稳定性提升到 95%。

**核心局限**：
- **能定位 JSON，但修不了内部语法错误**（尾逗号、单引号、注释）
- **解决不了内容语义错误**（格式对但字段值不对）
- **也处理不了前置污染**（对话式开场白仍然在正文中）

### 3.4 第四阶段：纵深防御管道（稳定性 99.99%+）

**思路**：既然没有任何单一方法能覆盖所有失败模式，那就**构建多层冗余，每层各管一类问题，每层都假设前一层可能失败**。

**实现**：
1. **事前约束**：在 prompt 和 API 层面最大程度减少坏输出（第 0 层）
2. **文本清洗**：去除对话式开场白、Markdown 污染等包裹性内容（第 1 层）
3. **结构提取 + 修复**：定位 JSON 边界，并修复常见语法错误（第 2 层）
4. **语义校验**：检查跨文件一致性、数学正确性（第 3 层）
5. **异常兜底**：当一切方法都失败时，调用廉价模型或返回 fallback 值（第 4 层）

**结果**：稳定性达到 99.99%+。

**关键突破**：仅在 prompt 中添加"禁止角色扮演式输出"这一项改动，就让格式稳定性大幅提升。**事前防御比事后清洗更有效**——这也是为什么把 Prompt 约束放在第 0 层（最先执行）。

## 4. 架构总览：Russell锦囊·纵深防御管道⭐⭐

经过 4 个阶段的演进，我们得到了一个**5 层纵深防御管道**。每一层都专注一类问题，每层都假设前一层可能失败，各自独立兜底。

```
┌─────────────────────────────────────────────────────────────┐
│                    LLM 原始输出                              │
└───────────────┬─────────────────────────────────────────────┘
                │
                ▼
┌─────────────────────────────────────────────────────────────┐
│  第 0 层：事前约束（Prompt + 原生结构化输出）                  │
│  核心职责：从源头降低坏输出概率                                │
│                                                           │
└───────────────┬─────────────────────────────────────────────┘
                │
                ▼
┌─────────────────────────────────────────────────────────────┐
│  第 1 层：文本清洗                                            │
│  核心职责：去除包裹性污染（对话开场白、Markdown 污染）          │
└───────────────┬─────────────────────────────────────────────┘
                │
                ▼
┌─────────────────────────────────────────────────────────────┐
│  第 2 层：结构提取 + 修复                                     │
│  核心职责：定位 JSON 边界，修复语法错误                        │
└───────────────┬─────────────────────────────────────────────┘
                │
                ▼
┌─────────────────────────────────────────────────────────────┐
│  第 3 层：语义校验                                            │
│  核心职责：检查跨文件一致性、数学正确性、字段完整性            │
└───────────────┬─────────────────────────────────────────────┘
                │
                ▼
┌─────────────────────────────────────────────────────────────┐
│  第 4 层：异常兜底                                            │
│  核心职责：模型兜底 / fallback 值 / 不抛异常                  │
└───────────────┬─────────────────────────────────────────────┘
                │
                ▼
             合格 JSON
```

> **成本权衡提示**：纵深防御能提升成功率，但每一层都有耗时与 Token 成本。实践中的平衡法则：**强模型场景（如 GPT-4o + 结构化输出 API）可酌情裁剪轻量清洗步骤；小模型或高风险场景建议保留完整纵深防御**。

下面 5 章我们逐层展开。每一层都会回答三个问题：**解决什么失败模式？怎么解决？效果如何**？

## 5. 第0层-事前防御: Prompt 约束 + 原生结构化输出

### 5.1 解决什么失败模式？

- **2.2 对话式开场白**（最主要）
- **部分 2.3 JSON 语法问题**（通过明确格式约束减少）
- **部分 2.4 Markdown 污染**（通过禁止不必要格式减少）

### 5.2 两个层级的约束

事前防御分为两个层级，约束强度递增：

**层级 A：Prompt 级约束**（靠指令引导模型自觉遵守）

在 system message 中明确添加：

```
重要：禁止角色扮演式输出。不得使用"XX专家已就位""我将激活XX角色"
"基于XX角色的独立判断"等对话式前缀。直接以结构化分析内容开始输出。
角色定义仅供参考，不要复述或回应。

重要：输出末尾必须包含 <!-- METADATA --> + ```json 代码块。
```

在 prompt 末尾强制给出**防呆模板**（8 行固定格式，不允许增减字段）：

> 注：这是锦囊项目所需的字段，大家各自的项目各自设计。

```
### 关键结论摘要
- 项目定义：{一句话产品定义}
- 可行性判定：{通过/有条件通过/不通过}
- 市场规模：{TAM/SAM/SOM 核心数字}
- 竞品差异化：{我方差异化锚点}
- 价值定位：{定位语}
- 商业模式：{定价策略 + 盈亏平衡}
- 风险：{最高风险 + 对冲方案}
- MVP：{最核心的 2 个功能}
```

**层级 B：API 级原生结构化输出**（模型侧强制约束，语法合规性接近 100%）

使用 OpenAI / Anthropic 等提供的结构化输出 API：

```python
response = client.chat.completions.create(
    model="gpt-4o",
    messages=[...],
    response_format={
        "type": "json_schema",
        "json_schema": {
            "name": "metadata",
            "schema": {
                "type": "object",
                "properties": {
                    "step": {"type": "integer"},
                    "market_size": {...}
                },
                "required": ["step", "market_size"]
            }
        }
    }
)
```

### 5.3 两种约束的本质区别

| 维度 | Prompt 级约束 | API 级结构化输出 |
|------|-------------|-----------------|
| 强制力 | 引导性，模型可能不遵守 | 强制性，模型侧保证 |
| 语法合规率 | ~95% | ~100% |
| 适用场景 | 任意模型 | 支持该 API 的模型 |
| 限制 | 无 | 只能输出 JSON，不能混合正文 |

### 5.4 为什么 API 级约束仍需后续层？

即使 API 级结构化输出保证了**语法合规率接近 100%**，后续层仍然不可或缺：

- **输出可能被截断**：长 JSON 触达 `max_tokens` 限制时，API 会返回不完整的 JSON
- **字段语义可能错误**：语法对但值不对（如把 SAM 填到 TAM 字段）
- **跨文件一致性问题**：多个 step 之间的数据可能不一致（step2 和 step5 报告的启动资金不同）
- **对话式开场白**：部分 API 模式下，模型仍可能在 JSON 前后附加文字

**结论**：API 级约束能消灭**大部分第 1 层和第 2 层的工作**，但**第 3 层语义校验**和**第 4 层兜底**永远不能省略。

## 6. 第1层-文本清洗：去除包裹性污染

### 6.1 解决什么失败模式？

- **2.1 标志位变异**（部分）
- **2.2 对话式开场白/结束语**
- **2.4 Markdown 格式污染**

第 1 层的任务就是把这些"包裹性污染"剥离，得到干净的文本。

### 6.2 清洗流水线

第 1 层按顺序执行 5 类清洗任务，每类专注一种污染：

**任务 1：移除对话式开场白/结束语**

识别并移除 9 种常见对话模式：
- "好的，作为XX专家，我将..."
- "好的，我将..."
- "基于以上分析，我将..."
- "当前为XX模式，我将作为XXX..."
- "作为XX专家，我将..."
- "XX专家已就位。"
- "我将遵循XX模式，执行Step N..."
- "首先，我将激活XX角色..."
- "基于XX的独立判断，我现在为您整合..."

**任务 2：移除 METADATA 块**

无论 METADATA 是什么格式（标准 ```` ```json ```` 代码块、`<!-- -->` 注释、裸 JSON），一律定位并移除——因为它不属于正文。

这里会用到括号栈算法（详见第 7 章）来定位 JSON 边界。

**任务 3：移除 Markdown 代码块包裹**

处理 LLM 把整段正文误包在 ```` ``` ```` 里的情况：

```python
# 只移除以 markdown 标题开头的代码块（避免误删真正的代码示例）
def unwrap_content_code_blocks(text):
    def replacer(match):
        body = match.group(1).strip()
        if re.match(r'^#+\s', body):  # 以 ## 或 ### 开头
            return body  # 提取内容，移除反引号
        return match.group(0)  # 其他保留
    return re.sub(r"```(?:json)?\s*([\s\S]*?)\s*```", replacer, text)
```

**任务 4：修复列表缩进**

把 4 空格缩进的嵌套列表改为 2 空格，防止 Markdown 渲染器把子列表误解析为代码块。

**任务 5：处理未闭合的代码块**

如果文本以 ```` ``` ```` 开头但没有闭合，移除开头的 ```` ``` ````。

### 6.3 防御性检测：宁可漏删，不可误删

第 1 层最重要的设计原则：**只在确认是污染时才移除**。

例如移除 METADATA 块时，必须验证：
- 解析后是合法的 JSON 对象
- JSON 中含 `"step"` 字段（METADATA 的特征标识）

否则宁可保留，也不要误删正文中的示例代码。

**误删正文内容的后果远比保留一些"垃圾"严重**。⭐

### 6.4 效果

- 覆盖率：99%+ 的包裹性污染
- 误删率：< 0.1%
- 性能：单次清洗 < 10ms（纯正则 + 字符串操作）

## 7. 第2层-结构提取：定位并修复 JSON

### 7.1 解决什么失败模式？

- **2.1 标志位变异**（核心）
- **2.3 JSON 本身的问题**（核心）

经过第 1 层清洗，文本已经干净了，但 JSON 可能仍然：
- 没有标志位，需要定位边界
- 含语法错误（尾逗号、单引号、注释）
- 嵌套结构复杂，正则搞不定

### 7.2 三层提取防御链

提取 JSON 也采用三层防御，**从精确到模糊**逐步降级：

**L1：代码块摘取**（最精确）

如果 JSON 在 ```` ```json ```` 代码块里，直接摘取：

```python
m = re.search(r'```(?:json)?\s*\n?(.*?)```', text, re.DOTALL)
if m:
    return m.group(1).strip()
```

**L2：关键字正则**（容忍格式变异）

如果知道 JSON 含特定 key（如 `"step"`），用正则抓取：

```python
# 完整匹配
m = re.search(r'\{"step"\s*:\s*\d+.*?\}', text)
# 截断场景兜底（只匹配 key-value 对）
m = re.search(r'("step"\s*:\s*\d+)', text)
```

**L3：括号栈定位**（终极兜底）

如果前两层都失败，用括号栈法从任意位置找到第一个 `{`，跟踪括号平衡，提取完整 JSON 对象：

```python
def extract_json_by_bracket(text: str) -> str | None:
    """括号栈法：从文本中提取完整的 JSON 对象。"""
    depth = 0
    start = None
    for i, ch in enumerate(text):
        if ch == '{':
            if start is None:
                start = i
            depth += 1
        elif ch == '}':
            depth -= 1
            if depth == 0 and start is not None:
                return text[start:i + 1]
    return None
```

**为什么括号栈比正则可靠**：正则无法处理嵌套结构（JSON 内含嵌套对象时 `(.*?)` 会过早截断），但括号栈天然支持任意深度嵌套。

### 7.3 JSON 语法错误修复

提取出 JSON 文本后，还需要修复常见语法错误才能 `json.loads`。我们按**出现频率**优先级用正则预处理：

```python
def repair_json(text: str) -> str:
    # 1. 移除 JSON 内注释（// 和 /* */）
    text = re.sub(r'//.*?$', '', text, flags=re.MULTILINE)
    text = re.sub(r'/\*.*?\*/', '', text, flags=re.DOTALL)

    # 2. 移除尾逗号（对象和数组）
    text = re.sub(r',\s*}', '}', text)
    text = re.sub(r',\s*]', ']', text)

    # 3. 单引号替换为双引号（谨慎使用）
    # 仅在确认不会破坏字符串内容时使用
    text = re.sub(r"(?<!\\)'([^']*?)'", r'"\1"', text)

    return text
```

**注意**：语法修复有局限性。如果 JSON 错误太严重（如截断、嵌套混乱），修复后仍然解析失败，就进入第 4 层兜底。

### 7.4 取值兜底：当 json.loads 也失败

如果修复后的 JSON 仍然无法解析，我们还有一个**正则取值兜底**：

```python
def extract_value_by_regex(text: str, key: str) -> str:
    """即使 JSON 不合法，只要 key-value 模式存在就能提取。"""
    pattern = rf'"{re.escape(key)}"\s*:\s*"([^"]*)"'
    m = re.search(pattern, text)
    if m:
        return m.group(1)
    raise ValueError(f"无法提取 key={key!r}")
```

这是**语法修复失败后的最后一道防线**——只要 LLM 输出了 `key: value` 模式，就能拿到值。

### 7.5 清理层：白名单 + 截断

提取出的值（如项目名称）还需要清理，防止注入攻击：

```python
_NAME_WHITELIST = re.compile(r'[^\w一-龥\-\+\.]')

def clean_project_name(name: str, max_length: int = 15) -> str:
    name = name.strip()
    name = _NAME_WHITELIST.sub('', name)  # 只保留中文、英文、数字、短横线
    if len(name) > max_length:
        name = name[:max_length]
    return name
```

### 7.6 完整提取流程

```
原始文本
    │
    ▼
L1: 尝试摘取 ```json 代码块
    │成功 ──────> 得到 JSON 文本
    │失败
    ▼
L2: 尝试关键字正则匹配
    │成功 ──────> 得到 JSON 文本
    │失败
    ▼
L3: 括号栈定位边界
    │成功 ──────> 得到 JSON 文本
    │失败 ─────> 进入第 4 层兜底
    │
    ▼
JSON 语法修复（去注释、去尾逗号、修单引号）
    │
    ▼
尝试 json.loads
    │成功 ──────> 得到 dict 对象
    │失败
    ▼
正则取值兜底（按 key 提取）
    │成功 ──────> 得到字段值
    │失败 ─────> 进入第 4 层兜底
    │
    ▼
白名单过滤 + 长度截断
    │
    ▼
最终干净的值
```

### 7.7 效果

- 提取成功率：99.9%+
- 误提取率：< 0.01%
- 性能：单次提取 < 5ms

## 8. 第3层-语义校验：格式正确但内容不对

### 8.1 解决什么问题？

前面 3 层解决了**格式问题**（从乱七八糟的文本中提取出合法 JSON）。但格式正确不代表内容正确——LLM 可能输出：

- step2 说 TAM 是 500 亿，step0 说是 480 亿（跨文件不一致）
- 5 维度评分之和 ≠ 总分（数学错误）
- 启动资金在 step5/step6/step7 中各不相同（跨文件不一致）

这些是**语义问题**，需要专门的校验层。

### 8.2 三类校验规则

| 类别 | 规则示例 | 容差 | 严重度 |
|------|---------|------|--------|
| **单文件格式** | METADATA 存在性、JSON 合法性、摘要字数 | — | 高/中/低 |
| **跨文件一致性** | TAM/SAM/SOM 在 step2/step0/final_report 中一致 | 精确匹配 | 高 |
| **跨文件一致性** | 启动资金在 step5/step6/step7 中一致 | ±10% | 高 |
| **跨文件一致性** | 盈亏平衡时间在 step5/step6/step7 中一致 | ±1 月 | 中 |
| **数学正确性** | 5 维度评分之和 == total_score | 精确匹配 | 高 |
| **数学正确性** | LTV ÷ CAC ≈ 声明的比值 | ±20% | 高 |
| **合理性** | 年化 ROI ≤ 3年总 ROI | — | 高 |

### 8.3 模糊匹配：适应 LLM 的不精确性

LLM 输出的数字不可能每次都精确一致（如 step5 说"启动资金 2000万"，step7 说"1980万"）。**精确匹配会导致大量误报**，因此校验器使用了**分级容差**：

```python
# 启动资金：±10% 容差
if ratio > 0.10:  # 差异超过 10%
    report_failure("启动资金一致性", ...)

# 盈亏平衡时间：±1 月容差
if gap <= 1.0:
    report_success("盈亏平衡时间一致性", ...)

# LTV/CAC 比值：±20% 容差
if abs(computed - ltv_cac) > ltv_cac * 0.2:
    report_failure("LTV/CAC 比值验证", ...)
```

### 8.4 范围值 vs 精确值

LLM 有时输出范围值（如"第 8-10 个月"），有时输出精确值（如"9"）。校验器需要统一处理：

```python
def extract_breakeven_range(value):
    """统一转换为 [min, max] 范围。"""
    # 尝试提取范围 "8-10"
    range_match = re.search(r'(\d+(?:\.\d+)?)\s*[-~至到]\s*(\d+(?:\.\d+)?)', value)
    if range_match:
        return [float(range_match.group(1)), float(range_match.group(2))]
    # 尝试提取单个数字
    num_match = re.search(r'(\d+(?:\.\d+)?)', value)
    if num_match:
        v = float(num_match.group(1))
        return [v, v]
    return None
```

**校验逻辑**：将所有值转换为范围 `[min, max]`，计算所有范围的全局交集。有交集或差距 ≤1 月视为通过。

### 8.5 警告不阻断

校验失败时，只打印警告，**不阻断主流程**：

```
[OK]   METADATA 存在性: ✓
[WARN] METADATA 格式合规: ✓ 但使用旧格式...
[FAIL] TAM 跨文件一致性: step2=500亿, step0=480亿
```

**为什么**：PDF 导出是关键路径，宁可带点不一致也要让用户拿到报告。事后可通过校验报告定位问题。

### 8.6 效果

- 数据一致性检查覆盖率：100%
- 误报率：< 1%（通过模糊匹配容差）
- 性能：单次校验 < 50ms

## 9. 第4层-异常兜底：当一切方法都失败

### 9.1 解决什么失败模式？

- **2.5 其他场景**（截断、完全乱序、多段 JSON 等）
- **前 4 层全部失败**的边缘情况

正则和括号栈能覆盖 99% 的场景，但总有 1% 的极端 case（如 JSON 被截断一半、嵌套结构异常复杂）。这时需要**更智能的方法**。

### 9.2 轻量兜底：局部修复 + 二次解析

在进入重量级兜底前，先尝试一些轻量级手段：

- **截断修复**：如果 JSON 末尾缺 `}`，尝试补全
- **多次提取**：如果括号栈匹配到多个 JSON 对象，尝试每个，看哪个最完整
- **宽松解析库**：引入 `json5` 或 `dirty-json` 等第三方库，能解析更宽松的 JSON

### 9.3 重量兜底：模型自修复

当轻量兜底也失败时，调用一个**廉价模型**（如 DeepSeek-V4-Flash，每次调用 < $0.001）从全文中提取 JSON：

```
Prompt: "请从以下文本中提取 METADATA JSON 对象，只返回 JSON，不要其他内容。

文本：
{full_text}"
```

**为什么用便宜模型**：
- 这是兜底策略，不是主路径，成本不敏感
- 提取任务不需要强推理能力，小模型足够
- 比返回错误让用户重新运行要好

### 9.4 兜底的兜底：fallback 值

如果模型也失败了，使用预定义的 fallback 值，**永远不抛异常**：

```python
def extract_project_name(raw: str, fallback: str = "未命名项目") -> str:
    try:
        json_text = extract_json_block(raw)
        value = parse_json_value(json_text, "project_name")
        result = clean_project_name(value)
        if result:
            return result
    except (ValueError, KeyError):
        pass

    return fallback  # 全部失败，使用兜底值
```

**设计原则**：**永远不要抛出异常导致整个流程中断**。宁可用一个不完美但可用的值，也不要让用户体验断裂。

### 9.5 效果

- 最终兜底成功率：99.99%+
- 成本：每次兜底调用 < $0.001
- 用户体验：无感知（即使兜底也正常完成流程）

## 10. 设计原则

经过 6 个版本迭代，我们提炼出 4 条核心设计原则：

### 原则 1：纵深防御

**不相信任何单一环节的可靠性。**

LLM 输出本质是概率采样，任何单一方法都有失败概率。只有通过多层冗余，每层各管一类问题，每层都假设前一层可能失败，才能把单点失败概率降到极低。

### 原则 2：快速失败与优雅降级

**能修则修，不能修则明确失败，不静默产出错误数据。**

- 能修复的语法错误：尝试修复
- 不能修复的：进入兜底
- 兜底也失败：返回 fallback 值，但明确记录日志
- 跨文件一致性错误：打印警告但不阻断主流程

### 原则 3：与模型能力解耦

**解析层越强，对模型输出的依赖越低。**

这意味着：
- 强模型场景可以裁剪轻量清洗步骤（节省成本）
- 弱模型场景保留完整纵深防御（保证稳定性）
- 切换模型时无需重写解析代码

### 原则 4：成本权衡

**纵深防御能提升成功率，但每一层都有耗时与 Token 成本。**

实践中的平衡法则：
- **强模型 + API 级结构化输出**：可裁剪第 1 层部分清洗
- **强模型 + Prompt 级约束**：保留完整第 1-3 层
- **弱模型或高风险场景**：保留完整 5 层纵深防御

## 11. 可复用模式清单

以下是从实战中提炼的可复用模式，可直接移植到我们的 AI 应用中。

| 问题 | 模式 | 适用场景 |
|------|------|---------|
| LLM 输出含对话式开场白 | **角色禁用约束** | 在 system message 中明确"禁止复述角色定义" |
| 需要固定格式输出 | **防呆模板** | 在 prompt 中给出不可修改的模板，明确"不可增减字段" |
| 提取 ```` ```json ```` 中的内容 | **代码块摘取** | `re.search(r'```(?:json)?\s*\n?(.*?)```', text, re.DOTALL)` |
| 提取任意嵌套的 JSON | **括号栈定位** | 见第 7 章 `extract_json_by_bracket()` |
| 兼容多种历史输出格式 | **多格式渐进匹配** | 按优先级依次尝试多种正则/算法 |
| JSON 含尾逗号、单引号等 | **正则预处理修复** | 见第 7 章 `repair_json()` |
| 跨文件数据一致性 | **分级容差校验** | 金额 ±10%、时间 ±1月、比值 ±20% |
| LLM 输出范围或精确值 | **范围值统一化** | 统一转为 `[min, max]`，计算交集 |
| 校验失败但不影响主流程 | **警告不阻断** | 打印警告但继续执行 |
| 正则全部失败 | **模型兜底** | 调用廉价模型从全文提取 |
| 模型也失败 | **fallback 值** | 预定义可用的默认值 |
| 保证流程不中断 | **永远不抛异常** | 最内层 try-except 返回 fallback |

## 总结

LLM 结构化输出清洗的本质是**概率系统 vs 确定性期望**的矛盾。我们不能假设 LLM 会永远正确，我们只能假设它**偶尔会犯错**，然后为此构建多层防御。

**核心公式**：

```
可靠性 = 事前约束（95%） + 文本清洗（3.8%） + 结构提取（0.9%） + 语义校验（0.2%） + 异常兜底（0.09%）
       ≈ 99.99%+
```

每一层都在解决上一层的"漏网之鱼"，最终把成功率从 60% 提升到 99.99%+。

**记住**：在 LLM 应用中，**防御比进攻更重要**。与其花精力让 prompt 更完美，不如花精力让清洗管道更健壮。因为 prompt 我们永远无法控制 100%，但清洗管道我们可以。
